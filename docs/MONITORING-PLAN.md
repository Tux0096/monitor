# План реального мониторинга производительности

Замена текущих синтетических проб на измерения, отражающие то, что видят пользователи.

## Почему текущий подход не отвечает на вопрос

Проба делает `fetch` с сервера и меряет время до последнего байта HTML.
Это **не** скорость загрузки страницы. В замер не входит:

- выполнение JavaScript и гидратация,
- загрузка CSS, шрифтов, изображений,
- отрисовка,
- реальная сеть пользователя (3G, слабый Wi-Fi, дальний регион),
- реальное устройство (бюджетный Android против сервера в дата-центре).

Сервер в том же дата-центре, что и сайт, по оптоволокну — это лучший
возможный случай, а не типичный. Отсюда и разрыв: проба говорит 300 мс,
пользователь ждёт 4 секунды.

Второй дефект — **среднее вместо перцентилей**. Распределение времени
загрузки скошенное: один запрос на 12 секунд ломает среднее за сутки.
Именно это мы и наблюдали. Отраслевой стандарт — **p75** (Google
использует его для Core Web Vitals) и **p95** для API.

## Архитектура: три слоя

| Слой | Что отвечает | Когда работает | Источник правды |
|---|---|---|---|
| **RUM** | «Как быстро у реальных людей» | Есть трафик | ✅ да |
| **Синтетика** | «Не стало ли хуже после релиза» | Всегда | нет, но воспроизводимо |
| **Аптайм** | «Работает ли вообще» | Всегда | да, для доступности |

Текущая проба — это третий слой, ошибочно используемый как первый.
Её не выбрасываем, а понижаем до проверки доступности.

## Слой 1. RUM — один скрипт, два репозитория

Код сайта и приложения одинаковый, но **репозитория два и серверы разные**.
Приложение завёрнуто в Capacitor, поэтому `web-vitals` работает в обоих
случаях: в браузере и в WebView (Chromium на Android, WKWebView на iOS).

Практические следствия того, что репозиториев два:

- скрипт добавляется **дважды**, отдельным изменением в каждый репозиторий;
- релизы независимы — сайт и приложение будут какое-то время слать данные
  разных версий скрипта, сборщик должен принимать обе;
- есть риск расхождения копий со временем.

**Как избежать расхождения.** Два варианта, оба рабочие:

| | Копия в каждом репозитории | Скрипт с домена monitor |
|---|---|---|
| Расхождение версий | возможно | исключено |
| Внешняя зависимость | нет | есть (загрузка с it.franchise-fuji.ru) |
| Если monitor лёг | метрики идут | метрик нет, сайт цел |
| Релиз при правке скрипта | два релиза | ноль релизов |

Рекомендую **копию в каждом репозитории**: вы просили, чтобы ничего
не могло сломать сайт, а отсутствие внешних зависимостей — самая
надёжная гарантия. Скрипт около 30 строк, меняться будет редко.
Чтобы копии не разъехались, в теле запроса передаётся версия контракта
(`v: 1`), и сборщик отвергает неизвестные версии с понятной ошибкой в логе.

Если приоритет — не выпускать релизы ради правок мониторинга,
второй вариант тоже приемлем: скрипт подключается с `async`,
и его недоступность не блокирует страницу.

### Что собираем

| Метрика | Что означает | Норма (p75) |
|---|---|---|
| **LCP** | Когда отрисовался главный элемент | ≤ 2500 мс |
| **INP** | Задержка отклика на действие | ≤ 200 мс |
| **CLS** | Скачки вёрстки | ≤ 0.1 |
| **TTFB** | Ответ сервера | ≤ 800 мс |
| **FCP** | Первая отрисовка | ≤ 1800 мс |

Разрезы: платформа (`web` / `android` / `ios`), группа страниц
(`/catalog`, `/cart`, `/personal`), город, тип соединения (`4g`, `3g`),
версия приложения.

### Скрипт: требования безопасности

Вы просили, чтобы он ничего не сломал. Конкретные гарантии:

1. **Никаких сторонних CDN.** Скрипт раздаётся с вашего домена, вместе
   со сборкой. Нет внешней зависимости, которая может лечь или быть
   подменена.
2. **Не может бросить исключение.** Вся логика в `try/catch`, ошибка
   сборщика молча игнорируется. Падение мониторинга не должно ронять корзину.
3. **Не блокирует загрузку.** Подключается отложенно, отправка через
   `navigator.sendBeacon` — браузер шлёт данные в фоне, не задерживая
   переход по странице.
4. **Не блокирует выгрузку страницы.** `sendBeacon` не ждёт ответа.
   Фолбэк — `fetch` с `keepalive`.
5. **Размер ~2 КБ** в сжатом виде. Официальная библиотека Google.
6. **Никаких персональных данных.** Ни email, ни телефон, ни ID клиента.
   Только маршрут страницы, платформа, тайминги.
7. **Сэмплирование.** При большом трафике достаточно 10–20 % сессий —
   на перцентили это не влияет, объём данных падает в 5–10 раз.
8. **Отключается флагом.** Переменная окружения — выключить без релиза.

Схема подключения:

```
// один раз в корне приложения, общем для web и Capacitor
if (RUM_ENABLED) {
  try {
    const { onLCP, onINP, onCLS, onTTFB, onFCP } = await import("web-vitals");
    const platform = Capacitor?.getPlatform?.() ?? "web";
    const send = (metric) => {
      try {
        navigator.sendBeacon("/api/rum/vitals", JSON.stringify({
          name: metric.name, value: metric.value, rating: metric.rating,
          v: 1,                        // версия контракта, копии не разъедутся молча
          source: RUM_SOURCE,          // "site" | "app" — репозитории разные
          path: normalizePath(location.pathname), platform,
          connection: navigator.connection?.effectiveType ?? null,
          appVersion: APP_VERSION,
        }));
      } catch { /* мониторинг не должен ломать приложение */ }
    };
    onLCP(send); onINP(send); onCLS(send); onTTFB(send); onFCP(send);
  } catch { /* нет web-vitals — работаем дальше */ }
}
```

### Подводные камни origin

Данные придут с **четырёх разных origin**, и все надо разрешить в CORS:

| Источник | Origin |
|---|---|
| Сайт | `https://fuji.ru` |
| Приложение, iOS | `capacitor://localhost` |
| Приложение, Android | `http://localhost` |
| Веб-версия приложения, если есть | `https://app.fuji.ru` |

Пропущенный origin — самая частая причина «на сайте работает,
в приложении нет»: браузер отбрасывает ответ, ошибка видна только
в консоли устройства, данные молча теряются.

Поскольку серверы разные, `sendBeacon` идёт **кросс-доменно**.
Проверить, что сборщик отвечает на preflight-запрос `OPTIONS`
и отдаёт `Access-Control-Allow-Origin` для каждого из origin.

### Сборщик

Новый сервис `services/rum-collector` (порт 3105), по правилам
`AGENTS.md` — не в `app/`.

```
POST /rum/v1/vitals    — приём, без авторизации, с rate limit по IP
GET  /rum/v1/report    — агрегаты для дашборда, service secret
```

Защита от мусора: ограничение размера тела, белый список имён метрик,
отсечение значений вне разумного диапазона, лимит запросов с одного IP.

### Хранение

```sql
-- сырые события, живут 14 дней
CREATE TABLE rum_events (
  id           bigserial PRIMARY KEY,
  received_at  timestamptz NOT NULL DEFAULT now(),
  metric       text NOT NULL,          -- LCP | INP | CLS | TTFB | FCP
  value        double precision NOT NULL,
  rating       text,                   -- good | needs-improvement | poor
  path_group   text NOT NULL,          -- /catalog, /cart, ...
  platform     text NOT NULL,          -- web | android | ios
  source       text NOT NULL,          -- site | app (репозитории разные)
  connection   text,
  app_version  text
);
CREATE INDEX rum_events_recent_idx ON rum_events (received_at DESC, metric);

-- часовые свёртки с перцентилями, живут вечно
CREATE TABLE rum_rollup_hourly (
  hour        timestamptz NOT NULL,
  metric      text NOT NULL,
  path_group  text NOT NULL,
  platform    text NOT NULL,
  p50         double precision,
  p75         double precision,
  p95         double precision,
  samples     integer NOT NULL,
  PRIMARY KEY (hour, metric, path_group, platform)
);
```

Свёртка раз в час, перцентили через `percentile_cont`. Сырые события
старше 14 дней удаляются — иначе таблица съест диск (сейчас свободно 3.3 ГБ).

Оценка объёма: при 5000 сессий в сутки и 5 метриках — 25 тыс. строк в день,
около 5 МБ. За 14 дней ~70 МБ. С сэмплированием 20 % — 14 МБ. Приемлемо.

## Слой 2. Мобильное приложение — Firebase Performance

### Почему данных в дашборде нет (проверено на сервере)

Firebase собирает данные исправно — в консоли 50 тыс. замеров по каталогу.
До дашборда они не доходят по двум причинам, обе — отсутствующие учётные данные:

| Проблема | Проверка на сервере |
|---|---|
| `GOOGLE_SERVICE_ACCOUNT_FILE` указывает на `/opt/monitor/secrets/firebase-sa.json` — **файла нет** | `ls: No such file or directory` |
| `GOOGLE_SERVICE_ACCOUNT_JSON`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` не заданы, таблицы OAuth-токенов не существует | `relation "google_oauth_tokens" does not exist` |

Итог: `resolveGoogleApiAuth()` возвращает `null`, импорт помечается
`firebaseSkipped: true` и молча пропускается. Так с самого начала.

Отдельно `PAGESPEED_API_KEY` **не задан**, поэтому запросы к PageSpeed идут
без ключа и упираются в квоту: `429 Quota exceeded for 'Queries per day'`.
Поэтому и PageSpeed-данных нет ни строки.

Оба сбоя тихие: флаг в JSON-ответе и поле `pageSpeedError`, которые никто
не читает. Отсюда правило: **интеграция без учётных данных должна кричать,
а не пропускаться молча.**

### Что чинить

1. Создать сервис-аккаунт с доступом к BigQuery, положить JSON по пути
   из `GOOGLE_SERVICE_ACCOUNT_FILE`.
2. Включить выгрузку Performance → BigQuery в консоли Firebase.
   На тарифе Spark это работает через песочницу BigQuery бесплатно,
   но таблицы песочницы живут 60 дней — для истории нужен Blaze.
3. Добавить в дашборд статус интеграций: «Firebase: нет учётных данных»
   вместо тишины.

### Ограничение, которое никуда не денется

В консоли видно, что страницы приложения называются `localhost`,
`localhost/cart`, `localhost/catalog/*` — это origin WebView Capacitor.
Firebase не может отличить экраны приложения осмысленно, и постранично
данные бесполезны. Свой RUM с полем `path_group` эту проблему снимает.

Плюс баннер в консоли: «мы ограничили объём собираемых данных» — то есть
пайплайн Google может просесть в любой момент, а вы об этом узнаете постфактум.

Что даёт автоматически, без единой строки кода:

- время холодного и тёплого старта,
- время отрисовки экранов,
- длительность и успешность сетевых запросов,
- разбивка по версии приложения, устройству, стране.

Плюс ручные трейсы на ключевые сценарии: открытие каталога,
добавление в корзину, оформление заказа.

Отдельно стоит подключить **Crashlytics** — доля сессий без сбоев
(`crash-free sessions`) напрямую объясняет всплески обращений
категории «Мобильное приложение».

## Слой 3. Синтетика — настоящая, браузерная

Текущая проба заменяется на headless-браузер: Playwright или
Lighthouse CI, запуск раз в 15–30 минут (не каждые 10 минут по 3 сэмпла).

Зачем, если есть RUM:

- ночью и в низкий сезон трафика мало, RUM молчит,
- проверка сразу после релиза, до того как пользователи наткнутся,
- воспроизводимые условия: один и тот же профиль сети и устройства,
  поэтому регрессия видна чисто, без шума реального трафика.

Запускать отдельным контейнером с ограничением по памяти — Chromium
прожорлив, а на сервере 3.3 ГБ свободно.

Дешёвая альтернатива без своей инфраструктуры — **PageSpeed Insights API**
(бесплатно, 25 тыс. запросов в сутки) раз в сутки. Даёт и лабораторные
метрики, и разбор, что именно тормозит.

## Слой 4. Аптайм — то, что уже есть

Текущая проба остаётся, но меняет смысл: не «скорость», а «доступность».

- Интервал 1–2 минуты, один запрос вместо трёх.
- Пишем: код ответа, TTFB, факт доступности.
- Показываем: аптайм в процентах, инциденты, длительность простоев.
- Порог алерта: недоступность, а не «медленно».

Так исчезает подмена понятий, из-за которой мы месяц смотрели
на цифры, не значившие ничего.

## Слой 5. Связь с обращениями

То, чего нет ни в одном покупном мониторинге, а у вас данные уже есть.

Обращения категории `mobile_app` лежат в той же базе, что и метрики.
На одном графике: p75 LCP приложения и число обращений по неделям.

Практическая ценность:

- всплеск обращений после релиза объясняется цифрами, а не догадками,
- норма 0.02 % получает объяснение: не «курьеры жалуются»,
  а «после версии 3.4.1 время старта выросло вдвое»,
- видно обратное: жалобы есть, а метрики в норме — значит дело
  не в скорости, а в логике или UX.

Реализация тривиальна: обе выборки уже в `monitor_core`, нужен один
запрос с группировкой по неделям и вторая ось на существующем графике.

## Порядок работ

| # | Что | Эффект | Оценка |
|---|---|---|---|
| 1 | Перцентили вместо среднего в текущих графиках | Цифры перестают врать на выбросах | 0.5 дня |
| 2 | Проба → только аптайм, убрать из «скорости» | Уходит подмена понятий | 0.5 дня |
| 3 | CrUX API для fuji.ru | Реальные данные пользователей Chrome, **без единой строки на сайте** | 1 день |
| 4 | Сборщик RUM + скрипт в оба репозитория | Свои метрики, сайт и приложение | 3 дня + 2 релиза |
| 5 | Починить Firebase Performance → BigQuery | Метрики приложения, код уже есть | 1–2 дня |
| 6 | График «метрики против обращений» | Связь техники и бизнеса | 1 день |
| 7 | Браузерная синтетика | Ловля регрессий до пользователей | 2 дня |

Пункт 3 стоит сделать первым для быстрой проверки гипотез: CrUX даёт
реальные данные пользователей Chrome по домену за 28 дней, бесплатно
и без правок сайта. Если он покажет LCP около 4 секунд — значит
пользователи действительно ждут, и RUM подтвердит это точнее.
Если покажет 1.5 секунды — проблема локальна и надо искать сегмент.

  бэкфилл записывал сегодняшний замер под вчерашней датой.

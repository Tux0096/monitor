## 1. Почему некорректно считаются показатели сайта

Четыре независимых дефекта в `lib/firebase-performance-history.ts`. Первые два — основные.

### 1.1. Performance Score (0–100) записывается в поле миллисекунд

`queryPageSpeedDay()`, строка ~390:

```ts
rows.push({
  metricName: "Performance Score",
  sourceType: "site",
  avgMs: Math.round(performanceScore * 100),  // 0..100 в поле "миллисекунды"
  samples: 1,
});
```

Последствия:

- Балл попадает в `weightedAverage()` вместе с длительностями.
- В `buildPageMetrics()` сортировка `по currentMs desc` ставит балл (значение ~50–95) в один ряд с LCP (~2500).
- `isMetricSlow(score, "site")` сравнивает балл с порогом 1300 мс — балл **никогда** не «медленный», хотя балл 35 означает катастрофу. Семантика инвертирована: у балла больше = лучше, у длительности больше = хуже.

**Исправление:** вынести балл в отдельный `metricKind: "score" | "duration"`, исключить из порогов и из среднего.

### 1.2. Бэкфилл истории подставляет сегодняшние замеры в прошлые даты

```ts
export async function importMissingPageSpeedDays(from, to, force) {
  for (const day of enumerateClosedDays(from, to)) {
    imported.push(await importPageSpeedDay(day));   // ← day только как метка
  }
}

async function queryPageSpeedDay(day: string) {
  const data = await fetchPageSpeedReport(siteUrl, strategy);  // ← ЖИВОЙ запрос «сейчас»
  rows.push({ ..., day, avgMs: metric.avgMs });                 // ← клеим чужую дату
}
```

У PageSpeed Insights API **нет исторического режима** — он всегда меряет прямо сейчас.
Значит бэкфилл за 30 дней запишет 30 одинаковых строк с сегодняшними значениями,
и график «динамики сайта» станет вымышленным. Тренд и `deltaPercent` — мусор.

**Исправление:** запретить бэкфилл PageSpeed. Импортировать только за текущий день.
Для реальной истории — CrUX API (`chromeuxreport.googleapis.com`), у него есть исторический эндпоинт.

### 1.3. Две несовместимые системы измерения пишутся в один `source_type = 'site'`

| Источник | `app` | Что меряет | Типичное значение |
|---|---|---|---|
| PageSpeed (lab) | `pagespeed:mobile` / `:desktop` | LCP, TTI, Speed Index на эмулированном 4G | 2000–6000 мс |
| Synthetic probe | `probe:site` | TTFB и полная загрузка с сервера | 100–800 мс |

Обе группы сравниваются с одним порогом `site: 1300 мс`.
PageSpeed mobile **всегда** выше 1300 → постоянные ложные пуш-алерты,
которые к тому же съедают дедуп-ключи и приучают игнорировать уведомления.

**Исправление:** развести на `site_lab` и `site_probe` с разными порогами,
либо (проще) исключить `app LIKE 'pagespeed:%'` из алертов.

### 1.4. `.slice(0, 24)` отрезает реальные пробы

```ts
return pageKeys.map(...)
  .sort((a, b) => (b.currentMs ?? 0) - (a.currentMs ?? 0))
  .slice(0, 24);
```

PageSpeed отдаёт 10 аудитов × 2 стратегии + 2 балла = **22 строки**, и все с большими
значениями (2000–6000 мс), поэтому они занимают верх сортировки.
На probe-метрики сайта остаётся 2 слота из 24 — остальное просто не доходит до дашборда.

**Исправление:** лимит применять **после** группировки по `sourceType`, а не глобально.

### 1.5. Мелкое: фильтрация мусора на чтении вместо чистки данных

`isStaleSiteProbePage()` отбрасывает старые URL без `/samara/` при каждом чтении отчёта.
Строки остаются в БД и учитываются везде, где этот фильтр забыли применить
(а он применяется ровно в одном месте — `readPerformanceHistoryReport`).

**Исправление:** одноразовый `DELETE` + миграция, фильтр убрать.

## 2. Почему не работают пуши

### 2.1. Мёртвые FCM-токены никогда не удаляются (главная причина)

`services/push-notification-service/src/fcm.ts`:

```ts
if (response.ok) { sent += 1; continue; }
failed += 1;
errors.push(`${token.slice(0, 12)}…: ${response.status} ...`);   // и всё
```

FCM возвращает `404 UNREGISTERED` для отозванных токенов и `400 INVALID_ARGUMENT`
для битых. Токен ротируется при переустановке PWA, чистке данных браузера,
долгом простое. Такие токены остаются в `push_subscriptions` навсегда.

Через несколько недель `listPushTokens()` возвращает преимущественно мёртвые токены,
каждая отправка — цикл из неудачных HTTP-запросов, реальные подписчики теряются в шуме.

**Исправление:** при `404` / `400 INVALID_ARGUMENT` вызывать `removePushSubscription(token)`.

### 2.2. Ошибки отправки полностью проглатываются

`lib/push-service-client.ts`:

```ts
export async function notifyPushService(body) {
  try {
    await pushServiceFetch("/push/v1/notify", { ... });   // ответ не проверяется
  } catch {
    // push is best-effort
  }
}
```

Не проверяется `response.ok`, нет логирования. Если push-сервис лежит,
секрет разъехался или FCM отдаёт 401 — web об этом не узнает **никогда**.
Это объясняет, почему проблема не диагностируется.

**Исправление:** логировать `status` и тело при `!ok`, оставив best-effort семантику.

### 2.3. Последовательная отправка

Цикл `for (const token of tokens)` с `await` внутри. При 200 подписках и 300 мс
на запрос — минута на одну рассылку. У `/api/monitoring/probe` стоит
`maxDuration = 120`, у cron `*/10` — реальный риск наложения запусков.

**Исправление:** батчи по 50 через `Promise.allSettled`.

### 2.4. Нет диагностики

Нет эндпоинта, показывающего: сколько подписок, сколько живых, когда последняя
успешная отправка, какие ошибки. Отладка возможна только по логам контейнера.

**Исправление:** `GET /push/v1/subscriptions/health`.

## 3. Архитектура

### 3.1. `lib/appeals.ts` — 3894 строки, 83 прямых SQL-запроса, внутри web

Прямое нарушение `AGENTS.md` п.1 и `ARCHITECTURE.md` («Web — только UI и BFF-прокси;
бизнес-логика и персистентность — в backend-сервисах»).

Это самый крупный долг. В одном файле: чтение/запись обращений, слияние,
классификация, отчёты, статистика, санитизация точек, фильтрация админов.

**Направление:** выделить `services/appeals-service` (порт 3104, БД `monitor_core`).
Переносить итерациями по доменам, не одним куском:
`statistics → reports → merge → CRUD`. Web оставляет BFF-прокси.

### 3.2. Второй пул Postgres к внешней БД прямо из web

`lib/fuji-new-sync.ts` открывает соединение к боевой HR-базе (`fuji_new`)
из Next.js-процесса. Даже с read-only аккаунтом это связывает жизненный цикл
web-процесса с доступностью чужой БД и обходит слой сервисов.

**Направление:** перенести в отдельный воркер или в `appeals-service`.

### 3.3. Мониторинг живёт в памяти процесса

`lib/monitor/store.ts` держит снапшот в `globalThis`, `startMonitorLoop()`
защищён флагом `globalThis.__fuji_monitor_started`.

При pm2 cluster или втором инстансе: у каждого воркера свой снапшот,
`/api/health` отдаёт разное при каждом запросе, петля крутится N раз.
Сейчас работает только потому, что инстанс ровно один.

**Направление:** снапшот в Postgres или Redis; петлю — в отдельный процесс.

### 3.4. Пороги продублированы в двух местах

`lib/monitoring-thresholds.ts` и `services/push-notification-service/src/thresholds.ts`
содержат одинаковые константы. `packages/contracts` для того и существует,
но пороги туда не вынесены. Изменение в одном месте молча разъедется с другим —
дашборд будет подсвечивать одно, пуш слать другое.

**Направление:** перенести в `packages/contracts`.

### 3.5. Деплой-скрипты противоречат правилам

`package.json`:

```json
"deploy": "powershell -ExecutionPolicy Bypass -File scripts/deploy.ps1"
```

`AGENTS.md` требует «работать только онлайн, деплой на сервере»
через `bash /opt/monitor/scripts/server-git-deploy.sh`. PowerShell-скрипты
подразумевают сборку на ПК — противоречие с задокументированным процессом.

**Направление:** `npm run deploy` → ssh-вызов серверного скрипта, либо удалить.

### 3.6. Ноль тестов

Ни `vitest`, ни `jest` в `package.json`. Ни одного `*.test.ts` в `lib/`, `app/`, `services/`.
Нет CI.

Для кода, который считает нормы и шлёт алерты, отсутствие тестов на
`weightedAverage`, `buildPageMetrics`, классификатор и (будущий) расчёт нормы —
основной источник тихих ошибок вроде п.1.1.

**Направление:** vitest + тесты на чистые функции агрегации, дальше GitHub Actions.

### 3.7. Документация разошлась с кодом

`ARCHITECTURE.md` описывает `monitor-api:3102` — сервиса нет.
Указан порт push `3103`, в таблице сервисов — `3102`. Не описаны
`appeals`, Jira, MAX, Telegram, `fuji_new`.

## 4. Недельная статистика курьеров с нормой обращений

### Согласованные параметры

| Параметр | Значение |
|---|---|
| Норма | **0.02 %** = 0.0002 от числа заказов |
| В зачёт | только обращения с категорией `mobile_app` («Мобильное приложение») |
| Заказы | вводятся вручную, **одним числом на неделю** |
| Закрытие | закрытая неделя заморожена; переоткрыть может только админ, с логом |
| Вне закрытых недель | видно как «черновик», в сводные нормы не идёт |

Формула:

```
норма_обращений = round(заказы × 0.0002)
факт            = обращения (source = 'max', category = 'mobile_app', merged_into_id IS NULL)
отклонение      = факт − норма
статус          = факт ≤ норма ? "в норме" : "превышение"
```

### Схема БД (`monitor_core`)

```sql
CREATE TABLE courier_stat_weeks (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  week_start     date NOT NULL,              -- понедельник, Europe/Samara
  week_end       date NOT NULL,              -- воскресенье
  label          text NOT NULL,              -- "2026-W32"
  orders_total   integer,                    -- ручной ввод, NULL пока не заполнено
  status         text NOT NULL DEFAULT 'draft',   -- draft | closed
  appeals_total     integer,                 -- снапшот на момент закрытия
  appeals_mobile_app integer,                -- снапшот, идёт в норму
  norm_appeals   integer,                    -- снапшот расчёта
  closed_at      timestamptz,
  closed_by      text,
  reopened_at    timestamptz,
  reopened_by    text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (week_start)
);

CREATE TABLE courier_stat_week_audit (
  id         bigserial PRIMARY KEY,
  week_id    uuid NOT NULL REFERENCES courier_stat_weeks(id) ON DELETE CASCADE,
  action     text NOT NULL,        -- created | orders_set | closed | reopened
  actor      text NOT NULL,
  payload    jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

**Ключевое решение:** при закрытии недели показатели **фиксируются снапшотом**
в саму строку недели. Иначе позднее слияние или переклассификация обращения
задним числом изменит уже закрытую отчётность.

### API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/courier-stats/weeks` | список недель + статусы |
| POST | `/api/courier-stats/weeks` | сформировать неделю (draft) |
| PATCH | `/api/courier-stats/weeks/:id` | ввод `orders_total` (только draft) |
| POST | `/api/courier-stats/weeks/:id/close` | закрыть + снять снапшот |
| POST | `/api/courier-stats/weeks/:id/reopen` | переоткрыть (админ) |
| GET | `/api/courier-stats/summary` | сводка по закрытым неделям |

### Панель

`/dashboard/statistics` → вкладка «Недели»:

- список недель: период, заказы, факт `mobile_app`, норма, отклонение, статус;
- текущая неделя помечена «черновик», не входит в сводку;
- кнопка «Сформировать неделю» — создаёт draft за прошедший период;
- поле ввода заказов активно только в draft;
- «Закрыть неделю» — блокируется, пока `orders_total` пуст;
- у закрытой недели — кто и когда закрыл, кнопка «Переоткрыть» для админа.

### Порядок работ

1. Миграция + `lib/courier-stat-weeks.ts` (чистые функции расчёта + тесты).
2. API-роуты.
3. UI-панель.
4. Бэкфилл прошедших недель как draft.
